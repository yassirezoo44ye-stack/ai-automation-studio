## 1. Executive Summary

The suite is large (1488 backend tests + 111 frontend tests, ~57s/~12s respectively without coverage instrumentation) and, where it has been deliberately hardened — security, tenancy-boundary routers, billing webhook idempotency, circuit breakers — it is genuinely good: real reproductions, positive/negative pairs, explicit deny-by-default assertions. That work is not undone by anything below.

But the number that matters is not "1488 tests pass." It's this: **the entire backend test suite has zero real-database interaction.** Every single test mocks `asyncpg` — there is no test anywhere that runs a query against a real Postgres instance and checks the result. Line coverage overall is **61%** (branch coverage **57%**, measured, see §3), but that number is generous relative to what actually gets *exercised*: `app/tenancy/service.py` — the service every `org_context`/`require_permission` check in the app (including every fix from the last two security sweeps) ultimately calls into — sits at **17% line / 13% branch** coverage. The tests that certify tenant isolation mostly mock `TenancyService` itself rather than exercise it; the actual SQL that enforces "org A cannot see org B's row" has never been run.

This is the report's central finding, and it reframes everything else: **the suite is strong at "does the router call the right function with the right arguments," and weak at "does the underlying system actually enforce what we believe it enforces."** Two other production paths share that same blind spot at genuinely low measured coverage: the execution drivers that run a user's actual project (`python_script.py` 27%, `python_server.py` 21%, `detector.py` 17%), and the billing service methods handling real payment data (`credits.py` 29%, `invoices.py` 29%, `payment_methods.py` 27%) — all previously flagged qualitatively in the Testing Foundation Audit, now confirmed with real percentages.

**Coverage measurement itself is not wired into CI** — `pytest-cov` is an installed dependency and nothing more; the "Unit tests" CI step runs `python -m pytest tests/ -v --tb=short`, no `--cov` flag. Every number in this report had to be generated by hand for this assessment.

## 6. Mock/Fixture Risks

- **1,383 `AsyncMock`/`MagicMock`/`patch(` occurrences** across the backend suite (~0.93 per test). Concentrated in `tests/security/test_api_security.py` (224), `test_integrations.py` (97), `test_ai_gateway_migration_chat_build.py` (93). This is largely appropriate — these are unit tests deliberately isolating from I/O — but it means the suite's confidence is bounded by how faithfully each mock matches the real dependency's behavior. §5's `app/tenancy/service.py` finding is the sharpest example: dozens of router tests assert "the correct `TenancyService` method was called with the correct args," which is a real and valuable check, but is a different claim from "that method, when actually run, returns the correct thing."
- **77 `inspect.getsource`/`inspect.signature` occurrences across 10 files** — structural tests that check a dependency/decorator/gate is present (e.g. "this endpoint depends on `require_permission`") without exercising the code path behind it. This is a legitimate and cheap regression guard against someone silently deleting a security dependency (several of my own tenant-boundary-sweep tests use exactly this pattern deliberately), but it is not behavior coverage — a test that would pass if `require_permission("x", "y")` were replaced with `require_permission("x", "wrong-action")` (same decorator, wrong argument) is a real gap this pattern doesn't close.
- **Zero real-database tests anywhere** (§5 #1/#2, §7) is the single largest false-confidence risk in the suite: every `FakePool`/`FakeConn` (the convention established in `tests/test_idempotency.py` and reused throughout) implements only the exact query shapes its author anticipated. A query with a genuine SQL error, a typo'd column name, or a subtly wrong `WHERE` clause construction that still string-matches the fake's expected prefix would pass every test and fail only against real Postgres.

## 7. Integration Test Assessment

**As of the original assessment, none existed against a real database.** Confirmed by direct search: zero occurrences of a real `asyncpg.connect(...)` call succeeding against a live connection anywhere in `tests/`. The two places a real Postgres instance was touched at all:

Every "integration"-labeled test in `tests/` (`tests/test_integrations.py`, `tests/test_integration_webhook_recovery.py`) integrated across *application* layers (router → service → fake pool), not against real infrastructure.

## 9. Auth & Security Regression Coverage

This is the suite's strongest area and should be read as a positive finding, not folded into the gaps above. `tests/security/` (14 files, ~370 tests) covers: authentication (JWT, sub-token, OAuth callback failure modes), authorization/RBAC gating, tenant isolation (agent/memory/execution), webhook signature verification, rate limiting, prompt injection, provider security, cross-layer scenarios, and — as of the last two sessions — the full tenant-boundary sweep (30 tests) and the subscription-impersonation closure (6 tests). Positive/negative pairs, real reproductions before fixes, and explicit "404 not 403, can't distinguish doesn't-exist from isn't-yours" conventions are consistently applied. The one caveat is §5/§6's structural point: several of these tests verify a *gate is present*, and — per §7 — none of them verify the gate's *database-level* effect. The gate-presence layer is well covered; the enforcement-at-the-data-layer layer is not.

## 10. Reliability/Failure-path Coverage

Mixed, better than expected in places, worse in one specific spot:

- **Circuit breaker / bulkhead:** genuinely behavioral, not just structural — `test_reliability_wiring.py`'s `test_chat_run_agent_503s_without_calling_the_sdk` and `test_saturated_bulkhead_wins_before_the_engine_is_ever_called` actually exercise the failure path, not just confirm a decorator exists (alongside several `..._wired`/`..._has_bulkhead` tests that *are* structural — both styles present in the same file).
- **Retry/timeout:** `asyncio.TimeoutError`/`TimeoutError` handling appears in 12 files' tests, `retry`/`Retry` in 10 — reasonable surface coverage for provider-call retries and webhook redelivery semantics (`test_integration_webhook_recovery.py` is a good, real regression test for a specific past bug).
- **DB-transient-error retry (`app/core/maintenance.py::with_retry`):** effectively untested (§5 #7) — the one clear gap in this category, and notable because it's the function specifically written to survive the failure mode (a dropped Postgres connection) that §7 shows is never simulated against anything real either.
- **Malformed input:** 10 files reference malformed/invalid-payload handling — present but not systematic; no fuzzing, no property-based testing, spot-checks only (a reasonable choice for this stage, not a gap worth prioritizing above §5's items).
- **Cancellation:** covered narrowly (workflow step cancellation via the approval registry, execution cancel endpoints) rather than systemically.

## 12. Flakiness/Global-state Risks

No `@pytest.mark.skip`/`xfail`/`@unittest.skip` markers found anywhere — no known-broken tests are being silently carried. No `pytest-xdist` — the suite runs single-process, sequential, which is exactly why global-state hygiene matters and is inconsistently applied:

- **Good discipline exists:** `tests/test_rate_limit.py` uses an `autouse=True` fixture to clear `rl_store` before/after every test; `test_reliability_wiring.py`'s `TestCurrentHealthAccessor` saves/restores `health_mod._current_status` in `setUp`/`tearDown`; the tenant-boundary sweep's own new tests explicitly `.clear()` `WorkflowEngine._active`/`_plan_cache`/`_executions` in `setUp`.
- **Not universal:** no project-wide `conftest.py` fixture enforces this pattern — it's per-file discipline. A future test file that mutates a module-level singleton (`EventBus`, `CostRouter._decisions`, any of the several `_service`/`_registry` singletons across `app/`) without cleanup would be a latent order-dependency bug that only manifests depending on collection order, which is exactly the kind of failure that's expensive to debug later and cheap to prevent now.
- **12 files use real `time.sleep`/`asyncio.sleep`** for timing coordination (e.g. waiting for a workflow to reach its approval gate, or a rate-limit window to expire) — legitimate in most cases, but a source of occasional CI-load-dependent flakiness (a test sleeping 0.05s to "let a task reach a gate" can flake under a loaded CI runner).

No evidence of actual observed flakiness (no skip/xfail markers, no `pytest-rerunfailures` usage suggesting a known-flaky set is being retried) — this section is about latent risk, not a confirmed problem.
