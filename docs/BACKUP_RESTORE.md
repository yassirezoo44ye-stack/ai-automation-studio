# النسخ الاحتياطي والاستعادة — دليل التشغيل

هذا الدليل يغطي ما يجب حمايته في Flow، وكيف يُنسخ، وكيف يُستعاد خطوة بخطوة.
كُتب بعد فحص النسخ الاحتياطي (المرحلة الرابعة، 2026-11-17).

## ما يجب حمايته

| البيانات | المكان | الحماية |
|---|---|---|
| قاعدة البيانات: الحسابات، المؤسسات، المشاريع، المحادثات، الاشتراكات، ملفات PDF للمكتبة | Render Postgres 18 (`ai-studio-db`) | الاستعادة لنقطة زمنية (PITR) داخل Render، ونسخة يومية مشفّرة خارج Render (هذا الدليل) |
| ملفات المشاريع: الكود المولَّد، الملفات المرفوعة، الصور المولَّدة | `WORKSPACES_DIR` على قرص Render الدائم `/var/data` | لقطة يومية للقرص من Render |
| حزم التصدير المؤقتة | `dist_packages/` على قرص الحاوية | لا تحتاج حماية: تنتهي صلاحيتها ويمكن إعادة توليدها |
| الأسرار ومتغيرات البيئة | لوحة Render | احفظ نسخة في مدير كلمات مرور. الأسماء موثّقة في `render.yaml` |
| الكود والواجهة | GitHub + Vercel | تُبنى من git |
| الدفعات | Stripe | Stripe هو المصدر الأصلي |

## الإعداد لمرة واحدة

### 1. النسخة اليومية الخارجية لقاعدة البيانات

سير العمل `.github/workflows/db-backup.yml` يعمل كل يوم الساعة 02:17 UTC. وفي كل مرة:

1. يأخذ `pg_dump` من قاعدة الإنتاج.
2. يستعيد النسخة في قاعدة Postgres 18 مؤقتة ليثبت أنها تعمل.
3. يحفظ بصمة كل جدول (عدد الصفوف وmd5 للمحتوى).
4. يشفّر النسخة والبصمة بأداة `age`.
5. يحتفظ بالملف المشفّر 30 يوماً ضمن artifacts.

يحتاج سرّين في GitHub (Settings ← Secrets and variables ← Actions):

1. **`BACKUP_AGE_RECIPIENT`:** مفتاح عام من `age`. أنشئ زوج المفاتيح على جهازك:
   ```sh
   age-keygen -o flow-backup-key.txt
   # يطبع: Public key: age1...
   ```
   ضع السطر `age1...` في السر. أما الملف `flow-backup-key.txt` فهو المفتاح الخاص، ولا يوضع في GitHub أبداً. احفظه في مدير كلمات المرور وفي مكان ثانٍ، لأنه بدونه لا يمكن فك أي نسخة.
2. **`BACKUP_DATABASE_URL`:** من Render ← ai-studio-db ← Connect ← **External Database URL**.

بدون السرّين يتخطى سير العمل النسخ ويعرض تحذيراً، ولا يفشل. الجدولة تعمل فقط بعد دمج الملف في الفرع الافتراضي. لتجربة فورية: Actions ← Database backup ← Run workflow.

> إذا ضيّقت قائمة العناوين المسموحة للقاعدة في Render، فإن عناوين خوادم GitHub تتغير وقد يتوقف النسخ. القرار بين الأمرين لك، والتفاصيل في تقرير الفحص.

### 2. القرص الدائم لملفات المشاريع

`render.yaml` يعرّف قرصاً اسمه `workspaces` على `/var/data` بحجم 1 غيغابايت، ويضبط `WORKSPACES_DIR=/var/data/workspaces`. إن لم تكن الخدمة مُدارة عبر Blueprint، فأضف القرص يدوياً:

1. Render ← خدمة الويب ← **Disks** ← Add disk: الاسم `workspaces`، المسار `/var/data`، الحجم 1 GB.
2. Environment ← أضف `WORKSPACES_DIR` = `/var/data/workspaces`.
3. أعد النشر.

ملاحظات:
- الخدمة التي لها قرص لا تدعم النشر بلا توقف، فقد يتوقف الموقع ثوانيَ أثناء كل نشر.
- عند الإقلاع تجعل الحاوية القرص قابلاً للكتابة (`docker-entrypoint.sh`)، ثم تشغّل التطبيق بالمستخدم غير المميَّز `axon`.
- إن بقي `WORKSPACES_DIR` غير مضبوط في الإنتاج، يكتب التطبيق تحذيراً في السجل عند كل إقلاع.
- الملفات الموجودة اليوم على قرص الحاوية لا تُنقل تلقائياً. أي ملفات من قبل آخر نشر قد ضاعت أصلاً.

## الاستعادة

**قاعدة ذهبية:** استعد دائماً إلى قاعدة **جديدة فارغة**، وتحقق منها، ثم وجّه التطبيق إليها. السكربت `scripts/backup/db_restore.sh` يرفض أي قاعدة فيها جداول.

### أ. خطأ حديث (خلال آخر 3 أيام، أو 7 على Pro): استعادة لنقطة زمنية من Render

1. Render ← ai-studio-db ← **Recovery** ← Restore Database.
2. اختر وقتاً قبل الخطأ، فلا يمكن اختيار آخر 10 دقائق. يُنشئ Render قاعدة جديدة ولا يغيّر الأصلية.
3. تحقق من القاعدة الجديدة. من جهازك، وبعميل Postgres 18:
   ```sh
   scripts/backup/db_fingerprint.sh "<External URL للقاعدة الجديدة>" | head
   ```
4. خدمة الويب ← Environment ← غيّر `DATABASE_URL` إلى القاعدة الجديدة، ثم أعد النشر.
5. بعد التأكد من أن كل شيء يعمل، علّق القاعدة القديمة أو احذفها.

### ب. من النسخة اليومية الخارجية

تفيد هذه الطريقة إذا كان الخطأ أقدم من نافذة Render، أو إذا تعذّر الوصول إلى حساب Render.

1. GitHub ← Actions ← Database backup ← اختر التشغيل ← نزّل الملف `flow-<الوقت>.tar.age`.
2. فك التشفير:
   ```sh
   age -d -i flow-backup-key.txt flow-<الوقت>.tar.age | tar -x
   # يُخرج: flow-<الوقت>.dump و flow-<الوقت>.fingerprint.txt
   ```
3. أنشئ قاعدة Postgres 18 جديدة فارغة. على Render: New ← Postgres. ثم فعّل الامتداد إن لم يكن موجوداً: `CREATE EXTENSION vector;`.
4. استعد وتحقق، بعميل Postgres 18 أو عبر Docker:
   ```sh
   docker run --rm --network host -e TARGET="<External URL للقاعدة الجديدة>" \
     -v "$PWD:/w" -w /w pgvector/pgvector:pg18 \
     bash -c 'bash scripts/backup/db_restore.sh flow-<الوقت>.dump "$TARGET" flow-<الوقت>.fingerprint.txt'
   ```
   شغّل الأمر من مجلد المستودع بعد نسخ الملفين إليه، لأن السكربت موجود في `scripts/backup/`.
   النجاح يطبع: `verified: N tables match the backup exactly`. وأي اختلاف يطبع `MISMATCH` ويفشل.
5. وجّه `DATABASE_URL` إلى القاعدة الجديدة وأعد النشر، كما في الخطوة 4 من (أ).

### ج. ملفات المشاريع

Render ← خدمة الويب ← Disks ← **Snapshots**: اختر لقطة واستعدها. اللقطة تستبدل محتوى القرص كله.

## التجربة الدورية

مرة كل شهر، وبعد أي تغيير كبير في المخطط:

1. شغّل سير العمل يدوياً، فهو يجرّب الاستعادة بنفسه.
2. نفّذ (ب) كاملة على قاعدة مؤقتة.
3. سجّل التاريخ والنتيجة في `docs/LAUNCH_CHECKLIST.md`.

## نسخة يدوية من جهازك

```sh
# عميل Postgres 18 مطلوب، لأن الإنتاج يعمل على Postgres 18
scripts/backup/db_backup.sh "<External URL>" ./backups "<URL لقاعدة فارغة مؤقتة، اختياري>"
```
